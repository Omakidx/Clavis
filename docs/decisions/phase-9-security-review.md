# Phase 9 release security, privacy and policy audit — findings and dispositions

**Date:** 2026-10-23 · **Scope:** the whole extension as a release candidate (not a diff): secret boundary, the full route × sender matrix, privacy behaviour against [privacy-policy.md](../privacy-policy.md) and the Chrome Web Store User Data policy, built manifest and permissions, remote code, shipped dependencies, content-script exposure, extension-page XSS sinks · **Method:** independent read-only audit with code tracing, a scratch build and ZIP, Playwright probes (fake `gsk_TEST` keys, Groq intercepted), `npm audit`, and the existing security E2E and unit suites against the scratch build.

No Critical or High findings. Every fix from the Phase 2, 3, 5, 7 and 8 reviews is still in place. `npm audit --omit=dev` and `npm audit` report 0 vulnerabilities; no known advisory applies to the shipped versions (pdfjs-dist 6.4.299, preact 11.0.1, react/react-dom 19.3.1, scheduler 0.28.0, zod 4.6.7, wxt runtime 0.21.4).

| ID | Severity | Finding | Disposition |
| --- | --- | --- | --- |
| M1 | Medium (confirmed, release-blocking) | Nearby-text extraction skipped inputs and forms but not `contenteditable`, so an unsent draft next to the selection reached Groq as context on Explain — contrary to the privacy policy and §8 case 3. The selection check also missed `role="textbox"`. | **Fixed:** context skips `contenteditable`, `role="textbox"` and `isContentEditable` ancestors and returns nothing under `designMode`; the selection check also refuses `role="textbox"`. Unit tests and an E2E asserting the intercepted prompt contains no draft. |
| L1 | Low (confirmed) | WXT's content-script context always dispatches a document event named `<extensionId>:content:wxt:content-script-started`, so a site that knows the published ID can detect Clavis. | **Fixed:** observer and card are built as unlisted scripts (`observer.js`, `explain-card.js`) with no WXT context; a small runtime guard keeps the orphaned-script teardown. The Phase 5 L1 E2E now listens for these events too. |
| I1 | Info | `AI_EXPLAIN`/`AI_CANCEL` were accepted from options, onboarding and the popup, which never send them. | **Fixed:** content scripts, reader, practice page and side panel only. |
| I2 | Info | `TTS_SPEAK.voiceName` was accepted from every public sender and bypasses the on-device-only rule (D-22). | **Fixed:** `voiceName` only from options and onboarding (Test voice); other senders speak with the saved voice. |
| I3 | Info | The practice page's message listener accepted any sender from the extension. | **Fixed:** background only, like the reader and side panel. |
| I4 | Info | The extension-page CSP has no `connect-src`/`img-src`. | **Later:** consider `connect-src 'self' https://api.groq.com` (shared with the service worker; coordinate with `expected-permissions.json`). |
| I5 | Info | A page can restyle the toolbar host after a real selection to trick a click on Explain (cost: the user's quota; the page learns nothing new). | Accepted (rate limit, trusted events). |
| I6 | Info | Possible survival of the side-panel hand-off across same-page navigation without site access. | **Not an issue:** a real-UI test showed Chrome reports `status: 'loading'` and the URL under `activeTab` alone, so the hand-off is dropped. |
| I7 | Info | Requirements §8 case 4 still cited `isEvalSupported: false`, removed in PDF.js 6. | **Fixed** in the docs (no eval path; the ZIP audit checks for `eval`/`new Function`). |
| I8 | Info | The PDF.js chunk contains Node-only dead code referring to `@napi-rs/canvas`. | Accepted; explained in the store reviewer notes ([store/permission-justifications.md](../store/permission-justifications.md)). |
| I9 | Info | The shipped privacy-policy link is a placeholder. | **Open (Phase 10, D-15):** must resolve to the published policy before submission. |

**Privacy policy:** brought in line with the code — exact fields sent to Groq, complete storage list, a Permissions section (FR-074), a Limited Use statement, session-key and Clear-all-data corrections, side-panel lifetime and the no-site-access paths. **Store text:** single purpose, per-permission justifications, remote-code answer and data-use answers drafted in [store/permission-justifications.md](../store/permission-justifications.md).

**Verified sound:** permissions exactly `storage, tts, scripting, activeTab, contextMenus, sidePanel` + `https://api.groq.com/*` + optional http/https, each used; no `content_scripts`, `web_accessible_resources`, `externally_connectable` or `side_panel`; CSP per D-17; storage lockdown fails closed; a session-only key writes nothing to `storage.local`; the key never appears in replies or logs; the Groq fetch uses `redirect: 'error'`, no credentials, no referrer and a response cap; the only fetch target is `api.groq.com`; no `eval`/`new Function`; no HTML sinks in Clavis code; Clear all data sweeps both storage areas, aborts requests and clears the side panel.

**Needs a human:** whether Chrome's password manager offers to save the key on Settings; storage access level right after a browser restart; store dashboard data-use certifications, publisher name/email and Pages hosting (Phase 10); Windows/macOS voices (D-14).
